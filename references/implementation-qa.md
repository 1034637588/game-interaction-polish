# PixiJS + GSAP 实现与验证

## 接入原则

- 先核对项目版本和既有封装，再使用对应 API。渲染、命中测试、音频管理和业务状态沿用已有职责。
- 将“收到确定结果”和“播放结果演出”分开。表现层消费事件；动画完成、跳过或销毁不能重复发奖或提交业务操作。
- 一个显示属性有明确控制者。将基础布局、按压形变、命中形变和镜头偏移放在适当的独立变换层，避免多个 tween 相互覆盖。
- 为时间线定义重入策略：替换、合并、排队或忽略。策略按事件选择，不能用全局锁统一阻塞连续操作。
- GSAP 驱动时间线时避免再以 Pixi ticker 重复推进同一动画。不要为局部停顿改变全局时间缩放；明确保留输入、HUD 和不相关动画的运行。
- 将时间参数单位写清楚；如配置采用毫秒、GSAP 接口采用秒，在边界统一转换。
- 布局缩放与动画缩放分离；世界坐标转 HUD 坐标使用项目对应的坐标变换，验证不同屏幕比例。
- 场景销毁时清理本场景时间线、监听、音频、临时对象和滤镜，不停止其他场景的全局动画。池化对象归还时恢复透明度、缩放、旋转与滤镜状态。
- 跳过、取消、失败或切后台恢复均应落到确定状态；停止时间线本身不等于状态已正确复原。根据项目约定决定暂停、补齐或直接收束，不重播过期反馈。

## 性能与可读性

基于实际并发预算限制装饰粒子、声音和高成本滤镜；只在需要时采用对象池等优化。记录测试设备、分辨率与场景，不能把桌面顺畅推断为低端手机达标。

重要目标、接触点和结果不被特效持续遮挡。镜头运动、闪光和模糊的强度依据目标体验、显示设备与连续操作验证来选择，不能将普遍低强度当作专业平衡。尊重已有的减弱动态效果与静音设置；需要时提供关闭选项，避免不必要的频繁高对比闪烁。降低效果时保留必要的信息确认。

## 验证步骤

按改动范围选择检查，不需要为了一个按钮搭建完整测试平台。

| 情境 | 观察重点 |
| --- | --- |
| 单次操作 | 是否及时确认、接触清楚、结果可信、恢复自然 |
| 快速连续操作 | 动画争抢、反馈积压、声音叠加、输入误吞 |
| 多目标并发 | 焦点优先级、装饰合并、可读性与性能 |
| 取消/禁用/失败 | 未接受输入不伪装成功、对象不残留半完成状态 |
| 重复开始与跳过 | 最终结果一致、没有重复业务提交、旧演出不回调污染新状态 |
| 切后台/恢复/销毁 | 无过期补播、残余声音、漏清理或状态卡死 |
| 屏幕与输入适配 | 触屏不依赖 hover、命中区和视觉一致、HUD 飞行坐标正确 |
| 静音/减弱动态 | 核心状态仍清晰，关闭效果确实生效 |

为关键体验比较基础与打磨版本。比较响应、识别、连续操作和疲劳感，不以粒子数量或动画时长衡量质量。若用预录结果测试揭晓，标记为测试数据并保持业务算法不变。

强反馈任务按 [有效叠加与强度调优](impact-stacking.md) 组织组合、相位和强度比较。比较某一反馈因素时保持外部结果、输入路径及无关时序一致；有意改变制动、停顿或恢复时长时，将它作为独立变量记录。需要判断双通道是否互补时，比较基础、单通道 A、单通道 B 与 A+B，而不是只比较效果全关/全开。观察单次冲击与重复后的舒适度，不能只凭一帧截图给出最优结论。

使用可用的构建、类型检查或针对性测试验证实现；实际试玩验证手感。报告区分自动检查通过、观察到的体验、主观判断及未验证项。没有音频播放与听音证据，不写“视听同步已验证”。
